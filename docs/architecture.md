# Architecture

How RustyZoo is built, and the choices contributors share. What is not written yet is marked **Planned**. The plan and its progress are in the [milestones](https://github.com/RustyZoo/RustyZoo/milestones).

## Layout

One Cargo package, no workspace until a second consumer exists.

- The core library (`src/lib.rs`) has no platform code. It reads the game data and draws into memory.
- The program (`src/main.rs`) holds the commands and the window. SDL3 is used only here.

Modules of the core:

| Module | Role |
| --- | --- |
| `vfs` | Read-only file system over the loose files and archives of the install folder |
| `config` | Reader of the game's INI-like files (`.ai`, `.cfg`, `.lyt`, ...) |
| `award` | The awards (`awards.md` 3, 4): the definitions read from the `award*.cfg` files at start (`Catalogue::awards`, merged by id, a file counts with a `[Version]` above 0) and the held list of a zoo (unique, largest id first; `award::add`). The zoo reads its section from version 59 and writes it from the list. |
| `zoo` | Maps and saved games (`.zoo`): `Zoo::parse` keeps the header, the tiles, the entities' common part, the unit blocks of the units (`Common::unit`: goal, target, movement, pending call and behaviour set, positions as world positions with the ground height, the values the original writes for a field the version lacks, written back in the version's own form), the view, the clocks, the name counters and the money, and `Zoo::write` writes a file back in the version it was read in: the sections the engine does not model (habitats, shows, scenario, the rest of the game block, thoughts, research, marketing, cheats) and the body of every entity are kept as read (`Kept`, `Common::raw`) and the modelled fields written over them, so a file read and written is byte for byte the same (all 96 shipped files). An entity made in play has no body to write yet and fails the write. The engine drops the entities whose type is unknown when it writes (`Zoo::drop_unknown`). The `save FILE` and `load FILE` script commands of `sim` and `run` write and open a file Maps and saved games (`.zoo`): `Zoo::parse` keeps the header, the tiles, the entities' common part, the view, the clocks, the name counters and the money, and `Zoo::write` writes version 106 whatever the version read (70 and later): the sections the engine does not model (habitats, shows, scenario, the rest of the game block, research, marketing, cheats) and the body of every entity are kept as read (`Kept`, `Common::raw`) with the modelled fields written over them, and what the version lacks takes the value the original writes (the class fields are converted by the reader's copy, `zoo/upgrade.rs`), so a file of version 106 is written byte for byte as read (all 12 shipped ones; the name counters at 0 are not written, as the original does not). An entity made in play has its class fields built from the model, or the values of a new one from its type (`zoo/fresh.rs`, `World::finish_save`, which also gives a record of a transient type no body and takes every guest's record from its live state; a guest read from a file has the fields of the model written over the bytes it was read from, `fresh::guest`). An animal, made in play or read, is written from its whole record (`zoo/animal.rs`: the values, counters, the five counters not drawn (life, grow-up, birth interval, mate delay, crate), flags, breath, dates, escape record and home tile; the fields the engine does not model are kept as read in `spare`), over which `finish_save` puts the live animal (`Animal::record`); a new animal's counters are the ones its creation drew, once it has taken its first turn. A staff record is read whole (`zoo/staff.rs`: `StaffRecord`) and written from it in the form of 106, a field the version lacks taking the value of a new member; `finish_save` writes the live counters, assignments (the tile inside each gate, none for an exhibit without a gate), duty switches and group over it (`Staff::record`); the tour guide's layout of 106 is not seen in a file. Not upgraded yet: a version below 70, shows below 103 with scripts, a habitat with a show below 106. The thoughts load into the guests' list (those whose guest or object is not in the file are dropped, as the original does) and `World::saved` gives the zoo to write: the live thoughts, and the statistics (donations, spending, the count triple) and last service of each exhibit over its record, which is found by its first tile. |
| `pe` | Bounded reader for the resources of the game's resource DLLs |
| `strings` | The game's texts, merged from the `lang*.dll` libraries |
| `usertext` | The texts of user-created content: the language section of a `.uca`, `.ucb` or `.ucs` file (install language, user language, then `[defaultLCID]`), and the name, help and "the" texts served for the user name ids (19000 to 21999, numbered by the catalogue in `entity`) |
| `text` | Liberation Sans Regular and Bold (embedded) with the metrics of Arial: line height, baseline, whole-pixel advances; wrapping, alignment, clipping, shadow and drawing into a canvas; templates, numbers, money and dates (`text::format`, the month and weekday names from the user's regional settings, `text/format/locale.rs`) |
| `sprite` | Sprite files and palettes: decoding, drawing, tinting a palette, PNG output |
| `userdir` | The per-user folder: where it is, the settings written there, read over the game's `zoo.ini` |
| `cursor` | The original's mouse cursors, read at run time from the `res*.dll` libraries of the install: the image of a cursor number as pixels, `[UI] useAlternateCursors` (50 added to the number), the numbers of the cursors in use (no window) |
| `startup` | The start-up picture (a bitmap resource of the language and resource libraries), its progress bar, and the product version of the executable |
| `menu` | The main menu: what is set when it appears (background of the expansion flags, Continue and its tooltip, version label), what Exit does, the credits pages that replace one another on the interface clock, the scenario and freeform screens (`menu/screens`: lists, pictures, starting cash), and the files that Continue and Play ask the game to open; the load button of the main menu and Load Game show the freeform screen as a list of saved games (`menu::show_saved`), and `app/saves.rs` runs the save dialog (the name dialog, the question before a file that exists is replaced, the file written aside and renamed; Ctrl+S and Ctrl+L close the open panels first) and the list in play |
| `lists` | The data of those screens: the scenarios of `scenar*.cfg` with results and locks, the freeform maps of `free*.cfg`, the starting cash and its difficulty |
| `exhibit` | The regions of the map: tiles joined through sides without an exhibit fence form one region; the one with the entrance is the zoo grounds, the tiles beyond the zoo wall the exterior, every other region an exhibit with its number (kept while it exists), name, gate piece and size. The world builds them when a map opens, and after an exhibit fence is placed, removed or replaced it finds the regions again and matches them with the exhibits there were (`world/exhibit.rs`): a part cut off from the grounds is a new exhibit with a default name (`Event::New`) and a gate chosen by the walk round its boundary with the keeper reachability test once the player has named it (`give_gate`; the gate piece of a line that stays closed moves to the piece left on the line), an exhibit cut in two keeps the side of its gate, one opened to the grounds is deleted and two that join leave one (its gate piece turns back into a fence). An exhibit whose every boundary line holds a tank wall is a tank (`Exhibit::tank`; a show tank when its walls are show walls, `World::retank`), decided again after every fence change, for the maps' stored tanks too (`check-exhibits` compares both counts), and its default name says "Tank" or "Show Tank". The game asks about the objects a new tank does not allow before the name (`app/exhibits.rs`: Yes sells the scenery through the bulldozer's removal and puts animals and staff outside, anything else undoes the operation with its money, `World::decline_tank`). Each exhibit keeps its tiles in the original's fill order (`exhibit::fill`, started at the tile beside the placed piece, the survivor's tile of a removed one or, for an exhibit of a loaded map, its tile on the line the file closes last) and `Exhibits::boundary` reads its boundary pairs from that list; the levelling and refused objects of a new tank walk the tile list, its wall step the boundary list, the gate a land exhibit gets when its own moves into a new tank, the tile outside a new tank where units are put and the morph start take the first fitting pair. A morph without a gate starts at the changed line, stepped by the gate walk while outside the zoo, and a loaded exhibit whose record stores no gate gets the gate walk. An exhibit found in a loaded map takes its gate from its record (`load_gates`: the piece in the stored tile's slot of the stored side). Names follow the install language: a loaded map whose stored locale differs from it keeps none of its names, and each exhibit with a record gets the default name of its kind in that language (`World::name_loaded`), each entity the name of its type in it (`World::name_loaded_entities`, once the interface gave the type names); a save writes the install language and the names the exhibits have. `gate_for` says which exhibit a fence piece could be the gate of (one side in an exhibit, the other on the grounds, the slot across empty, not its gate already) and `move_gate` makes the piece the gate, the old one a fence again, and clears the undo list. The world only tells what happened (`take_events`); the game logs it, asks the name in a modal dialog inside the purchase of the piece that closed the exhibit (the rest of the drag waits and is bought after the answer, the gate and its messages) (`app/exhibits.rs`), and plays `sounds/exhibit.wav` once for each exhibit it asks the name of (base term 100: the original reads `completedExhibitAttenuation` and drops it, RustyZoo#109). `exhibit::rating` rates an exhibit for each species in it (habitat rating): `rate` takes a plain description (`Input`: the tile counts, the objects in the slots, the animals, and the types and the tiles of its amphibious neighbours) and gives a `Record` per species with the part scores, the shown suitability (`ceil(max(0, rating))`) and the recommendation bits; `State`, kept in `Exhibit::rating`, holds the 7 s rating timer and the 8 s species timer (`update(ms, rand, input)` takes the step and the simulation's draw as parameters, builds the description only when something is due and restarts a timer at `rand() % 200`), the species list with the tile of each ambient sound, the attractiveness, the assigned keeper and the time last serviced; `input` reads an exhibit of a world into the description. `check-rating <map>` prints the rating of every exhibit per species. `exhibit::viewing` builds the viewing areas of an exhibit (habitat rating 10: `Plan` is the exhibit and its path tiles, `areas` groups the path tiles within 2 tiles of a fenced tile into areas of at most 4 x 4 tiles, `Ground` is the heights and blockers of the map and `Area::observe` finds the exhibit tiles an area sees within 10 tiles in line of sight) and the fence deterioration state (`wear`, rule 12: sound, decayed or broken per exhibit); `Area::pressure` is the guest pressure on one animal for the unit code to apply. Nothing is cached: the callers build the areas again when a path or fence changes and call `wear` after a fence change and a load. `check-rating` also prints each exhibit's areas and deterioration. The world manager (`Sim::step_game`) calls `update` for the zoo grounds, then for every exhibit, at each step, and logs `sim rate ID [KEY SHOWN]...` for each rating it makes. `Exhibits::mark` marks an exhibit, and its amphibious and show neighbours, for a new rating (rule 4): the world calls it when an entity that is no guest, staff member or ambient creature is placed or removed in it, a tile of it changes, a filled tank with a gate gets a new wall height (not its water level or purity), and the units when a keeper finishes or an animal comes or goes; `refresh` rates a marked exhibit for a reader (a land exhibit's marked neighbour tanks with it, 9.2). An exhibit keeps a record of every species of its amphibious neighbours (5.1) and of its show neighbours (a tank's, and through its tank a land exhibit's: the tank's species, then those of the tank's show neighbours; `Input::show`, `Likes::via`) but rates its surrounding species list: its own species, for a land exhibit the amphibious ones of its tank and for a tank those of its show neighbours (9.2; a show tank rates an amphibious species 50 lower when it has no show neighbour), a land exhibit counts their water, murk and, for an amphibious species, scenery (5.3), the shelters and toys of every neighbour join its own (5.3), a tank refuses the water a species does not want (salinity, bit 11) and tells an amphibious species it has no land beside it (bit 63, 5.5.4); `rating` is the suitability an animal sees, the best of the land exhibits beside a tank for an amphibious species in it (rule 6). `before`, `entity` and `react` (and `terrain` around a terrain edit, `depth` for a new wall height), called by the placing tool, the Adopt and Hire tools, the drop of a unit picked up (not putting it back), the bulldozer and the staff panel's fire button, the terrain tool, the game's reading of the world's `Event::Depth` and the `tile` command of a test run, let the animals like or dislike an object, an animal, a staff member or a fence piece (which decides nothing by its value) placed or removed, a terrain change and the new wall height of a filled tank with a gate (9.4; an animal placed or removed decides an unchanged sum by the species' compatible animals list, negated for a removal, `Change`) as `Units::reactions`, which fade after 1250 ms and are drawn as faces above their animals (`Extra::faces`), and ask once per change for the approving or disapproving sound when an animal (not an egg) reacted (`Units::cheer`, `smile` or `frown`, played by the interface). `before` and `react` each mark the exhibit and its species list for revision, and the rating that follows (`refresh`, or the reading of a part of a dirty exhibit) revises the list first (5.1), which draws the tile of the ambient sound of a new type before the reachability test draws: `before` reads the sums through that rating, so one change rates each exhibit touched twice. `before` marks every exhibit touched before it reads any (a terrain change); `entity`, the pair of an entity, adds for an animal or a scenery piece (fences and tank walls included) in a tank each of its amphibious neighbours, read only, which compare their amphibious species only while the tank skips them; the sums are one table, the last neighbour's, and a land exhibit reaches the animals of a tank neighbour only when it is their home. `again` looks the exhibit of the piece's tile up once more before `react` (a fence piece that closes, opens or splits an exhibit leaves the tile in another one, and `again` rebuilds the whole after step from it: its tank test, its amphibious neighbours when the entity reads them, its rates flag; only the table of sums read before stays; `react` then marks and compares it). An entity placed or removed on the zoo grounds (a fence piece too) marks them and flags their species list, before and after, so their next update draws twice; a terrain change leaves them alone, and a refused placement runs neither. Every recomputation of an exhibit ends with its reachability test (`reach`, 5.8): it runs when the exhibit's escape check flag is set (a new exhibit, a change of its species or animal count, a fence piece removed, a terrain change, a new tank wall height, a fence piece that breaks, or that decays or is made healthy beside a species that bashes: `World::heal` itself, so the placing, the gate, the new game and the worker's mend all do) or at every 30th test (`rating::tests`, one counter for the program that no load or new game resets), draws a target among the tiles of 10.2 outside its amphibious neighbours (`viewing::candidates`) and lets the last animal of each type search its way there with its test flag up (`Finder::test`); the types that get there are kept in `State::escapes` for the escapes. |
| `world` | The map as the tools change it: the zoo with the "in the zoo" flag of every tile (a fill from beyond the entrance, stopped by exhibit fences), an index of the path, quadrants and edge slots of every tile rebuilt from the entities after each edit, the edit primitives (add and remove an entity, set a tile with the edge states of it and its neighbours written again and, when its shape or elevation changed, the objects on it put at the height of its ground again), the undo list of the last press and a dirty mark that makes the next draw stage the map again. It knows the tank exhibits (`tank_at`: the tiles of a tank are rigid for the terrain tools and come along in a non-contiguous step as a whole) and keeps the tank list the picture reads (`zoo.tanks`) in step with them. It links a tank and the land exhibit beside it whose ground is level with the tops of the tank's walls as amphibious neighbours (`world/amphibious.rs`, tank fauna 12: made again after every edit that can move a link), and the tank wall on the line is then a connector that amphibious animals cross. The same rebuild links a show tank and a plain tank that touch as show neighbours (`Exhibit::show_near`, exhibits and money 3.11: both filled and at least 4 high, wall tops at one level; also rebuilt when a tank is filled or drained), symmetric, never with a land exhibit; the portal wall pair is not made, a saved portal flag is only read and drawn. A new tank is made in `world/tank.rs` (3.9): its ground levelled and lowered by the `tanks.cfg` sink (recorded for undo) and painted with the floor type of its kind, its walls moved to its side of their lines or built anew where another tank stands (the gate that moved in is replaced), its water values (level 0, filled), and the objects it does not allow found (`refused`) before its name; the water itself is in `world/water.rs` (3.10): the app calls `step_water` once per simulation step not paused and not under a dialog, which moves each level one elevation step towards `H + waterOffset` (filled) or 0, `fill` and `drain` are instant while the game is paused, `set_height` cuts the water at once, `decay_water` takes a point off the purity of a tank that holds water every `waterPurityDecayTime` (`Exhibit::purity_ms`), every change of the purity goes through `set_purity` (cut to 0 and `initialWaterPurity`; the message 10549 once when the water gets too murky to see through), a level that comes back to 0 from above resets the purity to `initialWaterPurity` (every change of a tank's level or purity is a `world water ID level L purity P` line of a test run, and a change of the filled flag alone is not told), the picture puts a ripple (`render::add_ripples`, made at every staging) against every active wall of a tank that holds clean water, so they come and go with the level and the purity, and two tanks that merge get the mean height and the flag of the larger volume; the pending gate over a tank wall takes the tank height (`wall_height`) and is drawn as its stack with its own platform; a tank filter (`world/filter.rs`, tank staff 7; `Common::filter` holds its health and its two timers, which a record does not save: a loaded filter starts them at `cDecayTime` and `cFilterDelay` seconds, one placed in play at `cDecayTime` and 0) faces a tank and, at its place in the entity loop, cleans the water of a tank that holds water every `cFilterDelay` seconds by `cFilterCleanAmount` (`cFilterDecayedCleanAmount` once decayed), charging `cFilterUpkeep` as building upkeep at each cycle (`world filter ID HEALTH PURITY`), loses a point of health every `cDecayTime` seconds on or off, posts the events 10035 (decayed) and 10036 (broken, urgent) to the task pool and does nothing broken until a worker services it; a loaded filter that is decayed or broken posts its event again; the tank records the filter that serves it (`Exhibit::filter`, not saved: the first added that faces it while no live filter serves it, then each that updates), and a filter on a tank tile (flooded) or facing a tank another live filter serves (doubled) is removed at its update as the bulldozer removes it, with no refund and an undo record that holds its sell price of the moment, which an undo takes back (`world filter ID HEALTH PURITY flooded|doubled`); placing puts a filter only beside a tank no filter serves, facing it, and its sell price is halved once decayed and 0 once broken; a part cut off a tank takes the water of the tank, and an exhibit whose walls no longer fit its kind is replaced by one of the other kind (the morph). The camera picks a tile and world point from a window point. The undo list holds the actions of the last press and release (the first action after `begin` empties it): a placed entity (with the price paid), a removed one (its place in the list and the refund it gave), a piece that took the place of another (`swap`; a path laid on a path of the same type records nothing), tiles with their old state (a terrain stroke, a path's water painted dirt with no price, an accepted session, which holds the session's snapshot and cost), and the name and gate of an exhibit that a fence cut, or that a removed piece separated from another region, even when the line stays closed, or that a piece turned into a tank or a land exhibit of the other kind (a morph) (recorded before the piece, so the undo restores them after it); a wall brought to the tank's side is a `Moved` action, a wall the wall step copied a `Copied` one (its undo gives back the full price of its type), the removal of one of a tank's own walls first records the tank's purity, salinity, filled flag, wall height and base level (`Tank` actions, no price) and the levelling and floor of a new tank one tiles action without a price. `decline_tank` is a call of `undo`, and the game books the prices of the steps it returns. `priced` tells the price of the action recorded last. `undo` takes the actions back, the last first, and returns what it did with the prices for the game to move in the cash; the exhibits are found again quietly (no name asked, no gate chosen, the counter stays) before each recorded exhibit is given its name and gate. A removed entity is tried at the end of the list first and put at its old place only when it finds its quadrants, slot or path free; one that does not stops the undo (the rest of the list is kept) unless the list holds several removed entities, when it is passed over. The gate tool clears the list. Fence wear is in `world/wear.rs` (placing 7.4): `heal` makes a fence piece healthy (the strength and life of its type and a wear interval drawn from the game's generator between the `[Decay]` bounds of `fences/fence.ai`), `wear` runs for each piece at its place in the entity loop of `Sim::step_game`: a piece in the zoo whose type has a `cStrength` other than 500, that is no zoo wall, gate or tank wall and not `cIndestructible`, loses the step from its countdown and, at 0, one life and `cDecayDelta` strength, restarting at its interval, and breaks (life and strength 0) when its life falls below 1. The piece posts event 10033 when it reaches its decayed life and 10034 when it breaks (10034 for both on an electrified type), with the worker tile as data, on the channel the task pool reads; a zoo just loaded posts the same events for its pieces (`loaded_events`, posted by `Sim::fences_loaded` in entity list order with the cans' and filters' events, also by the `sim` command, after the load and before any fence is made healthy): 10034 for a piece with life 0 whose type can break (an exhibit fence that is no zoo wall, gate, tank wall or indestructible), else 10033 (10034 when electrified) for one at or below its decayed life. The test of the surroundings (placing open point 12.6) is not made, and the events 10033 and 10034, the break sound and the escape check wait for the staff and animal milestones; the exhibits' deterioration state is read from the pieces' life when asked. A scenario or freeform start whose map file has `resetfences` above 0, and the load of a file older than version 55 (its pieces have no condition), draw the interval of every fence piece (other starts, and the `sim` command, keep the stored pieces); a placed or replaced piece and every piece that becomes the gate of an exhibit, by the gate tool or by the game, when they are made healthy; the old gate keeps its values. |
| `money` | The cash (one `f32`) and the accounts: 31 categories, each with a ring of 12 months, a ring of 20 years and a total; charge (refused when the cash does not cover it), spend (never refused), refund and their undo book into a category and the net line; `can_pay` (a cost of 0 or at most the cash); the month change that clears the new month's column (the year's on January); the cash a start sets, never booked; the status bar text and its three colours. | `panel` | The information panels. `panel::exhibit` is the exhibit panel (information panels 3.5, 10) and the keeper recommendations plaque: `Panel` holds the current exhibit, the animal of the plaque and the refresh clocks (`Clock`: 10 s on the interface clock, not while the game is paused, a forced refresh at once and the next call again), `refresh` writes the list of the exhibits (name and the icon of its fence state, or of a tank's water purity: `tank_icon`), the name field, the construction date, the upkeep, keeper, popularity (the 11-picture half-star set) and donations of `exhibit::Stats` and the animal and thought lists into the layout (an exhibit that becomes current shows the selected tab's sub-layout and hides the others), writes the tank tab (`tank_tab`: the prices of `exhibit::price::Prices`, which buttons work, and by the filled flag either the fill group or the water name and the drain button; its presses are `app::tank_panel`'s, which pays them as construction and tells 10002, 10550 and 10551), and returns the `panel` log lines of what changed; `refresh_plaque` lists the recommendations (`recommendations`) of the animal's own stored sets (`Animal::advice` and `important`, the animal checks' bits included; no rating is done for it): the important bits first, in red, then the others, the lines about disliked scenery (`rating::disliked`) after the bits of their importance, or the well-suited text; an egg lists no scenery and ends with the single egg-care line (which also replaces the well-suited text); the texts name the animal itself. The panel shows no suitability and has no keeper button (13.5); a row of its animal list selects that animal. `panel::animal` is the animal panel (information panels 6, animals 13): `Panel` holds the selected animal and its 5 s clock, `bars` gives the four bar values and the colour of the suitability bar from the habitat check's thresholds, `band` the three "time ago" texts of the calendar time since the animal last ate and slept (`Animal::fed`, `slept`), and `refresh` writes the layout (the bars through `Interface::set_meter`, the tooltips with their value, the five newest thoughts about the animal) and returns its `panel animal` log line when something changed (the ids of the thoughts close it). `app/panel.rs` opens the exhibit panel (a release on the map with no tool picks the gate of an exhibit, which becomes the selected entity and carries the selection marker as any selected entity does (`render`: the marker is placed after the picture of any object or edge, by the footprint of the form of the animal: plain, egg (tested first) or crate, `EntityType::form_footprint`, from the background frame's offsets when the file has one); the exhibit list button), follows its list, name field and tabs, opens the panel of the unit selected (an animal, a guest or a staff member, `units_sync`; picking one up or closing the panel clears the selection) (the recommendations button shows the plaque, the exhibit button the exhibit panel, the follow button centres the camera on the animal at each interface pass and stops the keys and edge scroll), and calls `refresh` from the pass `panel::staff` is the staff panel (information panels 3.4, 9; `panel::follow` gives the follow button of the three unit panels the picture of the unit's type (`set_follow_icon`: its `idle` animation, else the base one, in the sprite file of facing 4 at rotation 0, first frame, never mirrored, whatever the unit does and the camera shows; `panel::guest` is the guest panel (information panels 8, guests 5.5): `Panel` holds the selected guest and its 10 s clock, `bars` gives the five bar values (happiness as a percentage of its range, each need as 100 minus its percentage), `stay` the band of the time in the park from the arrival date (`Date::millis`), and `refresh` writes the bars (with their tooltips), the time and favourite texts, the item pictures (each with its item name as tooltip, packed from the left; A moveable guest building is carried the same way (a second click on the selected building, or its panel's pick-up button): `building::lift` takes it out of the world, `Game::held` keeps it, `place::moved` is its pending object (judged as a new one, the facing it keeps on screen, cost 0) and the drop and the put-back set it down again (`app/carry.rs`); the panel's sell button is the bulldozer's removal of that one building without its `cDeletable` and zoo tests (`App::remove_one`). Log: `tool select ID`, `world carry ID`, `world drop ID X,Y` (with `home N` for an animal in an exhibit that is not a show tank) and `world putback ID X,Y`.|
| `intro` | The intro movies: which ones play (`[UI] playMovie`, `playSecondMovie`, their volumes) and the player that gives the picture due at a clock reading |
| `movie` | Intro movies: the AVI container, the Indeo 5 video decoded to RGBA pictures, the PCM audio (no window, no sound device) |

The core draws in software into an RGBA framebuffer (`Framebuffer`), as the original's software blitter does. The window only presents that framebuffer. Its pixels are the original's 16 bit screen: every colour drawn is reduced to 5-6-5 bits at once (`sprite::screen`) and kept as the 8 bit value the display shows (high bits repeated), and blends and shadows work on the codes behind it. There is no tint and no time-of-day setting. Every result can therefore be checked without a screen: text output, PNG pictures, hashes.

## Platform

SDL3 (window, input, audio) is built from source and linked statically, so no system SDL is needed. `run` plays a map in the window with the loop of the original; the keys of the map view become commands in `src/input.rs`, and the loop reads the cursor for the edge scroll. A run starts in full screen when `[user] fullscreen` of the ini file is not 0 (windowed run only), and every switch that succeeds is written back to the settings of the user folder. Full screen is switched by Alt+Enter or a script; the window is asked, and when it accepts (or reports on its own that it has switched, which is read from the window flags on every pass) the loop tells the game with a `fullscreen` command, so a log replays it. A full-screen window without the focus blocks the loop like a minimised one. The camera owns the two full-screen rules (edge band, zoom limit); `src/window/fullscreen.rs` places the picture on the display. A looping voice (the menu music) is refilled by SDL's get callback of its stream, on the audio thread, so it keeps playing, muted with the focus, while the loop blocks. `window-smoke` presents a test pattern.

### The window

`rustyzoo run <map>` (`src/window/`) plays the map in a window; `run` without a map starts up (the intro movies, then `src/boot.rs`: picture and progress bar, game data, interface) and opens the main menu, an `App` without a game that acts on what the menu's buttons select (a button that starts a game loads the file inside the click, hides the menu and starts the music's fade; Escape, the options panel's Main Menu and the window close ask first and No goes back to the menu, which `run <map>`, having none, answers by ending); `run --headless` (`src/run.rs`) runs the same `App::pass` on a scripted clock without any window, and prints the log lines that `run --log` also writes, so a log replayed headless gives the same frame hashes.

- **Loop.** As in the original: take every waiting event, run one `App::pass` (draw, interface, simulation timers against one clock reading), present a frame only when the pass painted one or the system asks for a redraw, then wait for an event or until the next timer is due. No spinning. While the window is hidden or minimised the loop blocks. That state is read from the window flags on every iteration, not tracked through the Minimized and Restored events, so it cannot stay asleep after a restore that comes as another event.
- **Cursor.** The window shows the cursor `App::cursor` names (over the interface the default, or the text cursor on an editable field; over the map view the terrain tool's by mode and button, the bulldozer's, the drag's, the pending object's, the hover one over a selectable entity, an exhibit under the assign tool or a fence piece under the gate tool, else the normal one; the busy cursor shows from the start-up, and `App` tells the window when a rotation or zoom of a map, or a load, begins; a save is never busy) from the install's libraries, the system arrow when one is missing (a warning, once). Ctrl+C switches to the alternate set anywhere and writes `[UI] useAlternateCursors` to the settings of the user folder. The tank-wall hover cursor is not shown yet.
- **Sizes.** The frame has the game size (the size of the ini file, cut to the usable area of the display, or `--size`), in a streaming texture that SDL scales to the output with the nearest pixel. The window is enlarged by a whole factor `k`: the display scale (the content scale of the display times its pixel density, read before the window exists) rounded, at least 1, and lowered until the window fits in the usable area. The window is asked for in points, `game * k / density`, with a high pixel density: on Windows and X11 (density 1, content scale 2 at 200%) that is `game * k` points, on macOS and Wayland (density 2, content scale 1) it is the game size in points. So the output has `game * k` pixels on every system, as large and as sharp as the original's window at that scaling. The mouse position is converted from points of the window to pixels of the game. The run checks that the renderer's output equals the window in pixels (a different size than `game * k` only warns, as with a fractional density), and prints the game size and `k`, the window size, its size in pixels, the output size, the display scale and the pixel density. `k` is fixed when the window opens, and a change of the display scale (another display, another setting) is not followed. The window can be resized: the game keeps its size, and the picture is scaled by the largest whole factor that fits and centred on black, the same placing as in full screen (`src/window/fullscreen.rs`), with the mouse mapped back the same way. The maximise button goes to full screen (the window is restored first, so leaving full screen gives a normal window); the zoom limit of a full screen is applied by that switch, and a plain resize does not change the game size, so it has nothing to check.
- **Measures.** `--timing MS` prints the gaps between the firings of each timer on the real clock (count, minimum, median, 95th percentile, maximum, the expected period, a histogram). `--shot FILE` reads back the presented pixels into a PNG. Both are information for a person or CI; no value fails a run.
- **CI.** Every system runs the window with the dummy video driver, the software renderer and the dummy audio driver, and checks sizes, painted frames and the replay of the log. One extra step per system opens a window on the runner's real video driver (X11 on a virtual display on Linux, Cocoa, Windows), reads the pixels back with `--shot` and logs the sizes, the scale, the number of colours and the hash (failing only if the window mode breaks or the picture is blank). A separate step on the dummy driver prints the timing summary of a ten second run. Pictures of game data are checked in CI, never published or committed.

## Game data

The game folder is the install folder, the one that holds `zoo.ini`. It is found with `--data <dir>`, then the `ZT_DATA_DIR` environment variable. **Planned:** a configuration file as a third source.

Files are looked up as the game does: in the directories listed in `[resource] path` of `zoo.ini` (the install folder itself if there is no such key), the earlier directory winning, ignoring letter case, with `/` or `\` as separator. Inside a directory the loose files come first, then the archives (`.ztd` and `.zip`); among the archives of one directory the one whose lower-cased name sorts last wins. Texts come from the resource DLLs, not from the archives. Nothing is ever written into the game folder: settings that RustyZoo changes go in the `zoo.ini` of the per-user folder (`userdir`), which holds only those keys and is put on top of the game's `zoo.ini` when the game is opened (`Vfs::overlay_ini`, keys compared ignoring letter case); see the README for the folders.

Everything read from a file is untrusted: malformed data gives an error, never a panic.

## Design choices

Not implemented yet unless said otherwise.

- **Entities.** No class hierarchy: one `Kind` enum (animal, guest, staff, scenery, building, ...) and flat properties read as the original reads them. Code branches on `Kind` only.
- **Behaviour scripts.** The scripts of the data are parsed at load time into an enum of operations and run by a state machine per unit. `behaviour` parses them when a definition file loads (the catalogue keeps them per file). The 53 operations of the program and the three misspelt names of the shipped data (`fFollow`, `fPlayWith`, `fPlayWithSoud`) parse; the three names and every call with defective arguments become a call that fails when run, as in the original, with a warning for the arguments. Any other unknown name is a load error that names the file, the section and the line. `behaviour::Runner` holds, per unit, the chain of sets being run (a nested set runs in place of its parent's current call, and a failure ends the whole chain), and `behaviour::Animation` the sequence being played, the queue and the base animation; each step the unit advances the animation, then executes the set, a done call letting the next start in the same step. The runner reads the sets, the ambient rows, the frames and delays of the animations and the sounds through the `Data` trait; `Library` implements it on the catalogue and the files and reads the frames of an animation when a unit first plays it. The map draws each unit with the animation and frame it holds (`Extra::shown`).
- **Simulation.** Like the original: a variable step (elapsed milliseconds times the speed factor, capped by `MaxSimTick`) and three independent timers (drawing, interface, simulation). A test mode with a fixed seed and fixed steps gives the same state hash on the three systems (`sim`, see Determinism).
- **Text** (from M4). Liberation Sans, which has the metrics of Arial, rendered with `fontdue` (no hinting, no SIMD, so the glyphs are the same on every system). The two font files are embedded unmodified with their licence in `fonts/`. A font is asked for by a face string and a size string as the layout files give them and cached per (face, size); glyphs are cached per font and character. Text is laid out and drawn into a canvas (`Framebuffer`) that the caller has filled with the background colour: smoothed edges blend towards the pixel underneath, so they blend towards the element's own background, as in the original. `text::format` writes the game's templates (`%s %d %m %r`, positional forms), integers, money and dates with fixed US English conventions, from the strings of the string table.
- **Beyond the original.** Improvements such as interface scaling come after parity.

## Determinism

`rustyzoo sim <map> --ticks N` steps a map without an interface, window or frame and prints one hash of the state (`sim::hash::state`: the tiles, entities, units, exhibits, money, zoo status, calendar, clocks, event queue and generator). The hash is FNV-1a over fixed-width fields, little-endian: whole numbers at their own width, a decimal value by the bits of its `f32`, a string or a list after its length as a `u32`. CI runs it on every map of both trials on Linux, Windows and macOS, with steps of 67 ms and of 1000 ms (the long run crosses two month changes), and the job `hashes` fails if the three differ or a map does not run. A `run` logs the same hash after each month change (`sim hash`), so that two runs of a played game compare by it; the source of the seconds of the seedings is left out, so that a replay of a test run hashes the same (each seeding shows in the generator). A new part of the simulation state goes into the hash in the same change, and a test shows that changing it changes the hash. The rules that keep it equal:

- Whole numbers of the original's widths (`i32`, `u32`, `u16`, `u8`); wrapping arithmetic where the original wraps, never an overflow that panics in debug and wraps in release.
- `f32` for money and the other decimal values, as the original, with the operations written in the original's order; no `f64` where the original has a single, no fused multiply-add.
- No transcendental float function (`sin`, `cos`, `tan`, `exp`, `ln`, `powf` and the like) in the simulation: their results differ between libraries. Square root, add, subtract, multiply, divide and comparisons are exact.
- No iteration over a `HashMap` or `HashSet` (the order differs at every run): a map is only looked up, and anything walked is a `Vec` in a fixed order (`ci/check-hash-iteration.sh` fails on a walk over a hash map in the simulation modules it lists; a walk whose order does not matter carries `// order-free: <why>`).
- The generator is the only source of chance (`sim::Rng`), seeded from the seed of the run, never from the clock or the address of anything (in play the clock's seconds are logged, and a replay seeds with them); the time is the sum of the steps.
- Nothing in the step reads the wall clock, the environment, a file or the draw.

## Dependencies

A dependency is added by the milestone that first uses it. Today: `sdl3`, `zip`, `png`, `flate2` and `fontdue`, and a trimmed copy of NihAV's Indeo 5 decoder in `vendor/nihav` (AGPL version 3 or later, pure Rust, no other dependency; see `vendor/README.md`), used by `movie`. ## Tests

- Unit tests build synthetic bytes in code.
- Tests on real data are `#[ignore]` and read `ZT_DATA_DIR`; run them with `cargo test -- --ignored`. They run on the English and the French install, picking expected values by the language of `lang0.dll`; `ci/gate.sh` runs them a second time on `ZT_DATA_DIR_FR` (step `full-fr`), and plays the freeform game of `ci/playable-full.txt` on each install with the release binary (steps `play` and `play-fr`: a game of thirteen months takes minutes, too long for a test in the debug profile); with a trials dir it also plays `ci/playable.txt` on base-trial and `ci/playable-tank.txt` on expansion-trial, as CI does (step `play-trials`).
- `README.md` and this document merge as a union (`.gitattributes`), so two changes to the same row do not conflict; `ci/check-doc-rows.sh` fails on a table row with the same first cell as another in its table, two bullets with the same bold lead in a section, or two command lines with the same command in a code block, which is what a union merge leaves behind.
- CI builds on Linux, Windows and macOS, runs `window-smoke`, and runs the commands on the two official trials (`ci/check-trials.sh`), including a windowed run on the dummy video driver, a timing summary and a window screenshot on the real video driver (see The window). In a job of its own beside the build, it plays the two games of `ci/playable.txt` (a freeform game to the thirteenth month) and `ci/playable-tank.txt` (a tank for three months) twice each and checks the log (`ci/check-playable.sh`; `docs/playing.md` says how a person plays the same); the job `hashes` fails if the last frame or state hash of a game differs between the systems.
- Nothing derived from the game is committed.
