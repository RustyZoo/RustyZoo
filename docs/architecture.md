# Architecture

How RustyZoo is built, and the choices contributors share. What is not written yet is marked **Planned**. The plan and its progress are in the [milestones](https://github.com/RustyZoo/RustyZoo/milestones).

## Layout

One Cargo package, no workspace until a second consumer exists.

- The core library (`src/lib.rs`) has no platform code. It reads the game data and draws into memory.
- The program (`src/main.rs`) holds the commands and the window. SDL3 is used only here.

The core draws in software into an RGBA framebuffer (`Framebuffer`), as the original's software blitter does. The window only presents that framebuffer. Every result can therefore be checked without a screen: text output, PNG pictures, hashes.

## Platform

SDL3 (window, input, audio) is built from source and linked statically, so no system SDL is needed. `run` plays a map in the window with the loop of the original; the keys of the map view become commands in `src/input.rs`, and the loop reads the cursor for the edge scroll. A run starts in full screen when `[user] fullscreen` of the ini file is not 0 (windowed run only), and every switch that succeeds is written back to the settings of the user folder. Full screen is switched by Alt+Enter or a script; the window is asked, and when it accepts (or reports on its own that it has switched, which is read from the window flags on every pass) the loop tells the game with a `fullscreen` command, so a log replays it. A full-screen window without the focus blocks the loop like a minimised one. The camera owns the two full-screen rules (edge band, zoom limit); `src/window/fullscreen.rs` places the picture on the display. A looping voice (the menu music) is refilled by SDL's get callback of its stream, on the audio thread, so it keeps playing, muted with the focus, while the loop blocks. `window-smoke` presents a test pattern.

### The window

`rustyzoo run <map>` (`src/window/`) plays the map in a window; `run` without a map starts up (the intro movies, then `src/boot.rs`: picture and progress bar, game data, interface) and opens the main menu, an `App` without a game that acts on what the menu's buttons select (a button that starts a game loads the file inside the click, hides the menu and starts the music's fade; Escape, the options panel's Main Menu and the window close ask first and No goes back to the menu, which `run <map>`, having none, answers by ending); `run --headless` (`src/run.rs`) runs the same `App::pass` on a scripted clock without any window, and prints the log lines that `run --log` also writes, so a log replayed headless gives the same frame hashes.

- **Loop.** As in the original: take every waiting event, run one `App::pass` (draw, interface, simulation timers against one clock reading), present a frame only when the pass painted one or the system asks for a redraw, then wait for an event or until the next timer is due. No spinning. While the window is hidden or minimised the loop blocks. That state is read from the window flags on every iteration, not tracked through the Minimized and Restored events, so it cannot stay asleep after a restore that comes as another event.
- **Sizes.** The frame has the game size (the size of the ini file, cut to the usable area of the display, or `--size`), in a streaming texture that SDL scales to the output with the nearest pixel. The window is enlarged by a whole factor `k`: the display scale (the content scale of the display times its pixel density, read before the window exists) rounded, at least 1, and lowered until the window fits in the usable area. The window is asked for in points, `game * k / density`, with a high pixel density: on Windows and X11 (density 1, content scale 2 at 200%) that is `game * k` points, on macOS and Wayland (density 2, content scale 1) it is the game size in points. So the output has `game * k` pixels on every system, as large and as sharp as the original's window at that scaling. The mouse position is converted from points of the window to pixels of the game. The run checks that the renderer's output equals the window in pixels (a different size than `game * k` only warns, as with a fractional density), and prints the game size and `k`, the window size, its size in pixels, the output size, the display scale and the pixel density. `k` is fixed when the window opens, and a change of the display scale (another display, another setting) is not followed. The window can be resized: the game keeps its size, and the picture is scaled by the largest whole factor that fits and centred on black, the same placing as in full screen (`src/window/fullscreen.rs`), with the mouse mapped back the same way. The maximise button goes to full screen (the window is restored first, so leaving full screen gives a normal window); the zoom limit of a full screen is applied by that switch, and a plain resize does not change the game size, so it has nothing to check.
- **Measures.** `--timing MS` prints the gaps between the firings of each timer on the real clock (count, minimum, median, 95th percentile, maximum, the expected period, a histogram). `--shot FILE` reads back the presented pixels into a PNG. Both are information for a person or CI; no value fails a run.
- **CI.** Every system runs the window with the dummy video driver, the software renderer and the dummy audio driver, and checks sizes, painted frames and the replay of the log. One extra step per system opens a window on the runner's real video driver (X11 on a virtual display on Linux, Cocoa, Windows), reads the pixels back with `--shot` and logs the sizes, the scale, the number of colours and the hash (failing only if the window mode breaks or the picture is blank). A separate step on the dummy driver prints the timing summary of a ten second run. Pictures of game data are checked in CI, never published or committed.

## Game data

The game folder is the install folder, the one that holds `zoo.ini`. It is found with `--data <dir>`, then the `ZT_DATA_DIR` environment variable. **Planned:** a configuration file as a third source.

Files are looked up as the game does: in the directories listed in `[resource] path` of `zoo.ini` (the install folder itself if there is no such key), the earlier directory winning, ignoring letter case, with `/` or `\` as separator. Inside a directory the loose files come first, then the archives (`.ztd` and `.zip`); among the archives of one directory the one whose lower-cased name sorts last wins. Texts come from the resource DLLs, not from the archives. Nothing is ever written into the game folder: settings that RustyZoo changes go in the `zoo.ini` of the per-user folder (`userdir`), which holds only those keys and is put on top of the game's `zoo.ini` when the game is opened (`Vfs::overlay_ini`, keys compared ignoring letter case); see the README for the folders.

Everything read from a file is untrusted: malformed data gives an error, never a panic.

## Commands

`ls`, `cat`, `dump-strings`, `strings`, `check-config`, `dump-sprite`, `check-sprites`, `movie-info`, `check-layouts`, `dump-layout`, `text-width`, `draw-text` and `window-smoke`; see the README. They read the data through the core and print text or PNG files, which is how the core is checked on real data.

## Design choices

Not implemented yet unless said otherwise.

- **Entities.** No class hierarchy: one `Kind` enum (animal, guest, staff, scenery, building, ...) and flat properties read as the original reads them. Code branches on `Kind` only.
- **Behaviour scripts.** The scripts of the data are parsed at load time into an enum of operations and run by a state machine per unit. An unknown operation is a load error that names it.
- **Simulation.** Like the original: a variable step (elapsed milliseconds times the speed factor, capped by `MaxSimTick`) and three independent timers (drawing, interface, simulation). A test mode with a fixed seed and fixed steps gives the same state hash on the three systems.
- **Text** (from M4). Liberation Sans, which has the metrics of Arial, rendered with `fontdue` (no hinting, no SIMD, so the glyphs are the same on every system). The two font files are embedded unmodified with their licence in `fonts/`. A font is asked for by a face string and a size string as the layout files give them and cached per (face, size); glyphs are cached per font and character. Text is laid out and drawn into a canvas (`Framebuffer`) that the caller has filled with the background colour: smoothed edges blend towards the pixel underneath, so they blend towards the element's own background, as in the original. `text::format` writes the game's templates (`%s %d %m %r`, positional forms), integers, money and dates with fixed US English conventions, from the strings of the string table.
- **Beyond the original.** Improvements such as interface scaling come after parity.

## Dependencies

A dependency is added by the milestone that first uses it. Today: `sdl3`, `zip`, `png`, `flate2` and `fontdue`, and a trimmed copy of NihAV's Indeo 5 decoder in `vendor/nihav` (AGPL version 3 or later, pure Rust, no other dependency; see `vendor/README.md`), used by `movie`. It is vendored because NihAV is not published on crates.io; the decoder is third-party code on untrusted data, so a panic inside it is caught and reported as a decode error.

## Tests

- Unit tests build synthetic bytes in code.
- Tests on real data are `#[ignore]` and read `ZT_DATA_DIR`; run them with `cargo test -- --ignored`.
- CI builds on Linux, Windows and macOS, runs `window-smoke`, and runs the commands on the two official trials (`ci/check-trials.sh`), including a windowed run on the dummy video driver, a timing summary and a window screenshot on the real video driver (see The window).
- Nothing derived from the game is committed.
